Research data is often unpublished, confidential or regulated. Helix is designed so that your data
stays on your machine or on servers you control.

## Summary

- **Usage analytics are opt-in.** Released builds ask before sending anonymous usage events, and
  send nothing until you accept. Builds you make from source never send usage data.
- **Your data stays local.** Helix never uploads files, prompts, agent output, terminal output,
  paths or project names to a Helix service.
- **Agents talk to their own providers.** When you use a cloud agent such as Claude Code or Codex,
  that agent sends your prompts and the files it reads to its provider, under that provider's terms.
  Choose a local model when that is not acceptable.

## Usage analytics in released builds

Builds downloaded from GitHub Releases show a banner on first launch asking whether to share
anonymous usage analytics. Nothing is sent until you accept, and you can change your choice at any
time in **Settings → Privacy**.

When enabled, Helix sends product events (for example "agent started" or "setting changed") to
PostHog. Every event carries only:

- the Helix version, OS, OS release and CPU architecture;
- a random install ID and session ID generated on your machine;
- event-specific fields from a fixed allow-list (counts, enum values, error classes).

Helix never sends file contents, prompts, agent or terminal output, paths, project names or account
identities. GeoIP lookup is disabled.

## Turning usage data off

Usage analytics also stay off, regardless of your choice in the app, when either of these is set:

- `DO_NOT_TRACK=1`
- `HELIX_TELEMETRY_DISABLED=1`

## Sensitive data

<Callout title="Planned: sensitive data mode">
  A per-project mode for human genomic, clinical and other regulated data is on the roadmap. It will
  force agents onto local models, block external network calls and database lookups, and show a
  visible badge while it is on. Helix will enforce it in the app, not just through prompts.
</Callout>

Until then, for sensitive projects:

- Use an agent configured with a local model (for example OpenCode or Goose with a local provider).
- Keep raw data on a server you control and work on it through an SSH host.
- Review what each agent is allowed to read before you start it.
